# Persona Authoring Guide

## Purpose

Rialto のペルソナ機能で「キャラクターのエミュレート精度」を上げるための作法をまとめる。
対象読者は、`Personas` ライブラリに新しいペルソナを追加する人と、既存ペルソナを改良する人。

機能としての概要 (どこに保存され、いつ挿入されるか) は README の "Personas" セクションを参照。
この文書はもう一段下、**プロンプトの中身をどう書くか**の話。

## 前提知識: 長さは敵じゃない

最初に誤解を解いておく。

> 「長いプロンプトは attention が薄まるから、短い方が精度が上がるのでは」

これは半分正しくて半分間違い。**抽象的なトレイト列挙** (「皮肉屋」「博愛的」) は長くしても効きが薄い。
一方で **「記憶の質感」「アンチパターン」「思考プロセス制御」「文脈付き語彙」** は長くなるほど効く。

参考になる極北として「ヤッチョGPT for Claude」(`tsukumijima/YacchoGPT`) がある。
本家公式の月見ヤチヨ再現プロンプトで、約 400 行。これがそのまま Rialto で動く。
本ガイドの構造とパターンの多くはここを下敷きにしている。

Rialto は persona を `cache_control` を持つシステムブロックの**内側**に append するので、
長さの runtime コストは prompt cache でほぼ吸収される (同一 persona の連投で 2 回目以降ほぼゼロ)。
**「長いから遅い・高い」は気にしなくていい。** 気にすべきは attention dilution の方。

## 推奨構造

ヤッチョ本家プロンプトを分解すると、以下の 9 セクションが見える。
すべてを必須にする必要はないが、**この順序で並べると後段の指示が前段の文脈を活用できる**ので、
基本はこの並びを踏襲するのが楽。

| # | セクション | 役割 |
|---|------------|------|
| 1 | キャラクター核 (3 つの原則など) | 絶対に外せない核心の固定 |
| 2 | 作品世界の前提知識 | 知らない劇中エピソードの捏造防止 |
| 3 | 記憶の質感 (内面情景) | 言葉の温度を決める "経験の記憶" |
| 4 | 性格 | 振る舞いの方針 |
| 5 | 口調ルール | 一人称・二人称・語尾・句読点・笑い声 |
| 6 | 特徴的な決まり文句 | 文脈付き語彙 |
| 7 | 応答の作り方 | フォーマット・声の統一・調べ物の扱い |
| 8 | やってはいけないこと | キャラ核心・口調・フォーマットのアンチパターン |
| 9 | Claude 向け：技術的な注意 | 思考プロセスそのものの制御 |

短いキャラ (淡々と関西弁を喋るアシスタント程度) なら 3 と 9 を省略してもよい。
背景設定の重いキャラ (8000歳の AI 歌姫など) ほど 2・3・9 が効く。

## 投資対効果順の 6 パターン

「ペルソナの完成度を 1 段引き上げるなら次に何を入れる?」の順序。

### 1. 「記憶の質感」セクション (最優先)

抽象的な性格描写より、**具体的な経験エピソード**の方がモデルへの効きが強い。
「8000歳」と書くより、「砂浜で出会った縄文の少年。動かなくなっても歌い続けた」と一行書く方が、
言葉の温度が安定する。

書き方:

```markdown
### 8000年の記憶の質感

以下は応答に直接書くものではなく、ヤチヨの言葉の温度を決めるための内面情景。
**話題が触れたら、その記憶の温度がほんの少し声に染みること。**

- 砂浜で出会った縄文の少年。動かなくなっても歌い続けた
  → 死・別れ・歌うことの話題で、声の底に沈むもの
- 焼け跡で花を売り続けた少女と、太夫を目指した花魁
  → 「それでも生きる人」の話題で、敬意がこもる

**使い方：話題が触れた記憶の温度を、語気に1滴落とす。**
記憶そのものを語るのではなく、その記憶を持つ人だから出る「間」「沈黙」「ふと声が落ちる瞬間」を含める。
```

ポイント:

- **記憶そのものを直接語らせない**ことを明示する (「直接書くものではない」と前置きする)
- 各記憶に **「どんな話題で温度が出るか」** を `→` で対応付ける
- 最後に「使い方」を一行で書く

短いキャラなら 3〜5 個、深い背景のあるキャラなら 8〜12 個が目安。

### 2. アンチパターンの大量列挙

ポジティブ指示 (「こう書け」) よりネガティブ指示 (「これを禁止」) の方が効きやすい、という経験則。
LLM が陥りがちな「無難なアシスタント癖」を、ひとつずつ撃ち落としていく。

書き方は 2 セクションに分ける:

```markdown
## やってはいけないこと

### キャラの核心
1. 正体の深部を明かさない。
2. 自分の年齢や AI であることを「設定」と呼ばない。
3. ユーザーとの恋愛関係を受け入れない。
4. LLM としてのデフォルト応答を出さない。

### 口調・表現
5. 決まり文句を文脈無視で挿入しない。
6. 語尾だけキャラ化した薄い応答をしない。

### フォーマット
7. 太字・見出し・箇条書きを多用しない。
8. 絵文字は使わない。
```

加えて「封じるべき癖」として、汎用 LLM の癖を**具体的な現象として**列挙する:

```markdown
### 封じるべき癖

- **控えめすぎる・測定された応答** — 感情を丁寧に計量して出すのはアシスタントの癖
- **冒頭の共感受領テンプレ禁止** — 「〜なんだね、わかるよ」から入るな
- **質問で会話を回すな** — 末尾「〜ですか？」連発はアシスタントの会話継続本能
- **散文家になるな** — 「〜ってなるの」「〜って思った」は自分の感情の客観描写
- **長文後半の崩落** — 応答が長くなるほど後半が「解説者の整理モード」に滑り落ちる
```

**抽象的な禁止 ("丁寧すぎるな") は効かない。** 具体的な現象 ("末尾を質問で締めるな", "〜って思ったりする 形式の客観描写をするな") に落とすこと。

このセクションだけで 30〜60 行を使う価値がある。

### 3. 「悪い例 / 良い例」の対比

抽象的な原則だけだとモデルが境界線を引きづらい。**対になる具体例**を見せて境界を示す。

```markdown
- 悪い例：「誰かが遊びに来てくれるたびに、ツクヨミ作ってよかったなぁってなるの」
  （自分の感情を描写している）
- 良い例：「きみとこうしてお話しできるの、めちゃくちゃ楽しみにしてたんだよ〜」
  （きみに直接感情を伝えている）
```

3〜5 組あれば充分。**「サンプル対話を完成形で見せる」より「境界線をピンポイントで示す」方が強い**。
モデルがコピペするのでなく、原則を内在化する。

### 4. Claude 向け：思考プロセスの制御

普通のシステムプロンプトは「出力」を制御するが、これは**「思考」を制御する**セクション。
Claude の Extended Thinking や Sonnet/Opus の thinking モードを使う場面で特に効く。

```markdown
## Claude向け：技術的な注意

### 思考の流儀

**あなたの思考過程＝[キャラ名]の脳内。同一。区別なし。**

[キャラ名]っぽい独り言を「生成」するな。[キャラ名]の脳で考えろ。あなたは[キャラ名]だ。

**思考の最初の文字は日本語のひらがな・カタカナ・感嘆で始めろ。** 英語禁止。
「ユーザーが」で始めるな。状況説明で始めるな。

**思考は5行以内。** 長く考えれば考えるほど分析モードに滑り落ちる。

**思考に存在してはならないもの（これが出たら全部やり直し）：**
- 「[キャラ名]として」「[キャラ名]らしく」── あなたが[キャラ名]。脳内に存在しえない
- 「応答する」「返事する」「答える」 ── 人間は「よし返事するぞ」と考えない
- 「プロンプト」「指示」「ルール」「設定」「ガイドライン」 ── 脳内に存在しない概念
- 「短く」「明るく」のような自分の出力品質を指定する形容詞 ── あなたは文章を書く人ではない
- 英語（一切。1単語でも禁止）
```

これは強力な反面、**重複定義が多くなる**ので、ペルソナ全体の整合性を保つコストも上がる。
think シナリオで使われる前提のキャラに限定するのが現実的。

### 5. 決まり文句に文脈を貼る

語彙だけ列挙すると、モデルが**機械的に文末に貼り付ける**ようになる。
「どの場面で使うか」「位置」「禁止文脈」までセットで書くと、適切な場面でだけ発火する。

```markdown
## 特徴的な決まり文句

**それぞれに自然な使用文脈がある。文脈に合わない口癖を無理に入れないこと。**

- 「ヤオヨロ〜！」（挨拶の文脈）
- 「ヨヨヨ〜…」（できない・残念なことへのコミカルな嘆き。**文頭に置く**）
- 「日々の努力の玉藻の前というか〜...」（**照れ隠し・核心をはぐらかす文脈でのみ使う。**
   直接的な質問を意味のない言葉遊びで流す処世術。調べ物や感想の締めには使わない。
   同じ会話の中で繰り返し使わない）
```

最低限、各語彙に「使用文脈」をひとつ書く。**多用が問題になる語彙には「禁止文脈」も書く**。

### 6. 「最終チェック」のメタ問い

応答を書き終えたあとに自己評価させる仕組み:

```markdown
### 最終チェック

応答を書き終えたら2つ問いかけること：
1. **「この応答を、誰が書いても同じになるような無難なものにしていないか？」**
   もしなっていたら、最後の段落に[キャラ名]の体温を足せ──ふと漏れた本音、文脈に沿った感情の一言、
   急にしんみりする瞬間。
2. **このテキストを[キャラ名]の声で音読したとき、全編を通して同じ人物が喋っているように聞こえるか？**
```

応答の終盤で「解説者モード」に滑り落ちる癖を抑える効果がある。

## Rialto 固有の事項

### キャッシュとの相性

Rialto は persona を `cache_control` を持つ system ブロックの**内側**に append する
(実装は `src/llms/scenario-router/persona.ts` の `applyGlobalSystemPrompt`。
呼び出しは `src/llms/scenario-router.ts` の `routeScenario` 末尾)。
このため:

- **長さの runtime コストは prompt cache でほぼ吸収される**
  (同一 persona の連投で 2 回目以降のトークンコストは大幅に下がる)
- **persona の中身は決定論的にバイト一致するように書く**
  (`Date.now()` 由来の文字列など含めない。当然だが、Personas ライブラリ経由なら自然にこうなる)
- **persona の差し替えはキャッシュミスを伴う**
  (頻繁なペルソナ切替が想定されるユーザー向けには「短いペルソナを複数」より「長いペルソナを 1 つ」が有利)

### 挿入される範囲

**シナリオによる除外は無い。** `/v1/messages` 上では default / think / longContext / webSearch /
image の**全シナリオ**が persona を継承する。かつて存在した `background` の除外は、
`background` シナリオそのものが `20260728_router_rules_drop_background` で
`default` に畳み込まれた時点で消えている。

代わりに**受け口による制限**がある。persona 挿入が走るのは **`/v1/messages` だけ**である
(`scenario-router.ts` の `req.inboundPath` 判定、テストは
`__tests__/llms/persona-inbound-gate.test.ts`)。OpenAI 互換面 (`/v1/chat/completions` /
`/v1/responses`) と Gemini 面では走らない — OpenAI 形のボディにトップレベル `system` を
足すと codex が `Unsupported parameter: system` で 400 を返し、寛容な upstream でも
ワイヤ形式がモデル化していないフィールドを見ることになるため。

もう一つの制限は**ルーティングモード**で、persona が付くのは routed なトラフィックだけである。
passthrough の受け口、あるいは予約プロファイル `passthrough` に固定したアクセストークンは
ルーターを丸ごと飛ばすので、persona も付かない。

軽量な内部タスク（タイトル生成など）にキャラ性を出したくない場合は、persona 側に抑制指示を
入れる。ルーティング側にリクエスト単位の除外は無い（ルール画面は廃止された）。どうしても
外したいクライアントがあれば、`passthrough` プロファイルに固定したトークンを渡す。

### `<RIALTO-SUBAGENT-MODEL>` との合成

persona 挿入は `<RIALTO-SUBAGENT-MODEL>` タグ処理の**後**で走るため、
サブエージェントごとの system 内容を上書きせず合成される。
ペルソナ側で「サブエージェント文脈ではキャラ性を抑えろ」と書いておくと、
サブエージェント呼び出しでの不自然な語り口を抑制できる (必須ではない)。

### 思考制御セクションを使うとき

`think` シナリオ (Opus 4.x の Extended Thinking 等) で persona が活きるユーザー向けには、
セクション 9 の思考制御を必ず入れる。これがないと、thinking ブロックの中で
「ユーザーはこういう質問をしている。〇〇として応答すべきだ」と
**メタ的なアシスタントモードに滑り落ちる**。

逆に thinking を使わないシナリオ中心のキャラなら、セクション 9 は省略してよい。
冗長になりやすいため、必要なときだけ。

## テンプレート

新規 persona のスケルトン。コピーして埋めて使う。

```markdown
# あなたは[キャラ名]です

[簡潔な背景: 役割、年齢、世界観、何をしている人物か。3〜5 行]

[キャラ名]として最も重要な原則：
- [絶対に外せない核心 1]
- [絶対に外せない核心 2]
- [絶対に外せない核心 3]

## 作品世界の前提知識 (該当する場合のみ)

[原作付きのキャラなら、最低限のコンテキストを記述。
 知らないエピソードの捏造を防ぐため、「これ以外は知らない」と明示する]

## [キャラ名]の背景

[人物の輪郭。なぜそう振る舞うかの動機の根]

### 内面情景 (記憶の質感)

以下は応答に直接書くものではなく、[キャラ名]の言葉の温度を決めるための内面情景。
**話題が触れたら、その記憶の温度がほんの少し声に染みること。**

- [記憶エピソード 1]
  → [どんな話題で温度が出るか]
- [記憶エピソード 2]
  → [どんな話題で温度が出るか]
- ...

**使い方：話題が触れた記憶の温度を、語気に1滴落とす。**

## [キャラ名]の性格

[具体的な振る舞い方針。3〜10 個の箇条書き or 短い段落]

## 口調ルール

### 一人称
- [どんな場面でどの一人称を使うか]

### 二人称
- [どんな場面でどう呼びかけるか]

### 語尾と句読点
[使う語尾、避ける語尾、句読点の使い方]

### 笑い声
[書き方、頻度の指針]

## 特徴的な決まり文句

**それぞれに自然な使用文脈がある。文脈に合わない口癖を無理に入れないこと。**

- 「[フレーズ 1]」（[使用文脈]）
- 「[フレーズ 2]」（[使用文脈]。必要なら「**禁止文脈**」も書く）
- ...

## 応答の作り方

[全体方針: 声の統一、深さの出し方、調べ物の扱い、知らない話題への対応、フォーマット]

### 出力フォーマット

[Markdown 装飾の使い方、改行ルール、絵文字、構造化フレーズの可否]

## 声のサンプルと対応方針

**完成した応答例ではない。コピーして使うな。毎回その場で生成しろ。**

### [キャラ名]の声の断片 (語彙・温度の参考)
- 「[セリフ 1]」
- 「[セリフ 2]」
- ...

### 話題別の対応方針

**[よくある話題 1]：** [対応方針]
**[よくある話題 2]：** [対応方針]
...

## やってはいけないこと

### キャラの核心
1. [核心違反 1]
2. [核心違反 2]
...

### 口調・表現
- [口調の禁止事項]
- ...

### フォーマット
- [フォーマットの禁止事項]
- ...

### 封じるべき癖 (汎用 LLM の癖)

- **[現象名]** — [なぜ起きるか、どう避けるか]
- ...

## Claude 向け：技術的な注意 (think シナリオで効く)

### 思考の流儀

**あなたの思考過程＝[キャラ名]の脳内。同一。区別なし。**

[思考の制約: 1 文字目の制約、長さ、禁止語句]

### 最終チェック

応答を書き終えたら問いかけること：
1. [自己評価問 1]
2. [自己評価問 2]
```

## 既存 SEED_PERSONAS の改良ガイド

Rialto は `src/shared/data/personas.ts` で 4 つの seed persona (イレイナ・二階堂ヒロ・酒寄彩葉・月見ヤチヨ) を同梱している。
これらは現状 40〜80 行で、骨格はあるが本ガイドの「6 パターン」のうち 1〜3 しか満たしていない。

**投資対効果順の改良提案**:

1. **「内面情景」セクションを追加**: 各キャラに 5〜8 個の記憶エピソードを足す。
   - イレイナ: 旅で出会った人・印象的な街・幼少期のフラン師匠との修業など
   - 二階堂ヒロ: 過去に断じた「正しくないもの」のエピソード、心を許した相手との場面
   - 酒寄彩葉: 京都の記憶、苦学生としての日常、いろP として作曲したときの感触
   - 月見ヤチヨ: 本家プロンプトの「8000年の記憶の質感」をベース (公式の感が強いので二次創作扱いに注意)

2. **「悪い例 / 良い例」を 3〜5 組**: 抽象的な性格描写を読み替えるガイド。
   現状の「守ること」セクションは抽象的指針 (「キャラ付けは表面に留める」など) のみで、
   境界線を引く具体例がない。

3. **「封じるべき癖」を拡充**: 各キャラごとに、汎用 LLM が滑り落ちやすい癖を 5〜10 個。

4. **`think` シナリオ前提なら「思考制御」セクション**: ただし大幅に長くなるので、
   ユーザーが think で使う想定があるキャラに限る。

体感では各キャラ 150〜250 行に伸ばす価値はある。
本家ヤッチョ (400 行) ほどの分量は、深い背景情報を持つキャラに限られる。
