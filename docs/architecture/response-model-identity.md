# 応答モデル ID の意味

Rialto には、似ているが意味の違う三つのモデル ID がある。

| 値 | 意味 |
| --- | --- |
| request model | クライアントがリクエストで指定した ID。ルーティングが有効なら、これは最終的な行き先を決めないことがある。 |
| selected model | Rialto がその試行で選んだ `provider,model`。429 などで failover した場合は、成功した後続候補を指す。 |
| response model | Rialto がクライアントに返す最終ルーティング先。本文では素のモデル名、ヘッダーでは `provider,model`。 |

## `/v1/models` はカタログである

`GET /v1/models` は現在有効で呼び出せる素のモデル名の一覧を返す。これはクライアントが
選べる候補を知るためのカタログであり、特定の一回のリクエストを実際に処理した候補の証明ではない。

シナリオルーティング、アカウントローテーション、failover により、リクエストごとの成功候補は
カタログの複数候補のどれでもあり得る。

## 応答での扱い

成功した completion のレスポンス整形時に、Rialto は成功した invocation の素のモデル名を
wire format のモデル値として常に返す。upstream が応答にモデル ID、別名、版番号を含めていても、Rialto は
最終ルーティング先で上書きする。

これは Claude Code などのクライアントが、リクエストした alias ではなく Rialto がそのリクエストを実際に
送った先を記録・表示できるようにするためである。最初の候補が失敗した場合でも、成功した後続候補のモデル名が返る。

本文にプロバイダ名を含めないのは、使用量の集計ツールのためである。Claude Code などのクライアントは応答の
`model` をそのまま会話ログに書き、Claude Code 自身の金額推定や、T3 Code のようにそのログから利用金額を
出すツール（LiteLLM の価格表を使う）は、その値をモデル名として単価を引く。`claude-code,claude-opus-5-5` は
どの価格表にも一致せず、Rialto 経由の呼び出しはすべて単価なし（$0）として数えられていた。
`claude-code/claude-opus-5-5` も一致しない。LiteLLM の価格表が `/` 付きで持つのは `vertex_ai/` や `azure/`
のような自分のプラットフォーム名だけで、Rialto のプロバイダ名は持たないからである。
`/v1/models` が公開するのと同じ素のモデル名を返せば、どのツールでも単価が見つかる。

この規則は Anthropic Messages、OpenAI Chat Completions、OpenAI Responses、Gemini GenerateContent の
JSON と SSE に適用される。

Anthropic SSE では最初の `message_start` だけを書き換え、以後のバイト列はそのまま中継する。
大きな署名やツール入力のイベントが完成するまで、後続データを溜め込まない。
先行するデータのないレコード（コメントなど）と `ping` はそのまま返す。初期レコードが 64 KiB を超える場合、先行レコードが
32 件を超える場合、初期データを解釈できない場合、または途中で EOF になった場合は、元のバイト列を保持する。
この場合、本文のモデル値は書き換えない。ほかの SSE 形式では従来どおりイベント単位で書き換える。

実際の送り先のプロバイダは `x-rialto-selected-model` ヘッダーが `provider,model` で返す。Rialto 自身の
指定形式のままなので、クライアントはこの値を次のリクエストの `body.model` に入れて同じプロバイダを
名指しできる。どのプロバイダで処理されたかは RequestLog とアクティビティ画面にも残る。
